# Task: Finished-on-first-sight event backfill

**Status**: In Review
**Component**: collector
**Assigned to**: Claude
**Priority**: High
**Branch**: feature/finished-match-backfill (branched from `main` at `f7c9db9`, post PR #3 merge)
**Created**: 2026-07-11

## Objective

When the collector's poll loop first sees a match that is **already `FINISHED`** — no in-memory baseline, no stored row, never previously seen live — fetch its full event list once and write it through the normal reconcile/writer path, instead of silently recording only the scoreboard snapshot (score + status, zero events) as happens today.

**Scope limit (confirmed live, see Findings):** this plan covers a match that finished earlier **the same slate-day** and is therefore still present in ESPN's default (no-`dates`) scoreboard response. It does **not** cover a match that finished on a **prior day** and has already rolled off that response — that case is out of scope here and tracked under Follow-up Work. This is the same boundary the Requirements' cost-bound reasoning already relies on ("today's slate only"); that bound is also a coverage ceiling, not just a cost bound, and is stated explicitly here rather than left implicit.

## Context

The poll loop only calls `fetch_match_detail` (the event-carrying endpoint) for a match that is currently live, or was live and is transitioning to a terminal state (`was_live` / `in_transition`, `src/gamecollect/engine.py:1044-1092`). A match first observed already `FINISHED` — the collector started late, or the match ended before it was ever polled — skips straight past that branch:

```python
# src/gamecollect/engine.py:1067-1069
if match.status not in LIVE_STATUSES and not was_live:
    hydrated.append(match)
    continue
```

`match` here is the bare scoreboard snapshot from `fetch_live_matches` — for the real ESPN provider its `events` list is always empty (`_normalize_scoreboard_event`, `src/gamecollect_football/espn.py:862-951`, builds a `NormalizedMatch` with no `events=` kwarg, docstring "score only"). So a match that finished before the collector was watching gets a score/status row and **no goal/card events, ever** — the collector has already committed to never re-fetching this match's detail once a stored row exists, since it is no longer `was_live` on any future poll either.

**Why it matters:** the gamealerts intelligence-plane game-worker (PR #33) consumes `get_events_since` to answer "who scored / assists / highlights." A match that ended before the collector watched it yields only the scoreboard tier, leaving every event-level question about that match permanently unanswerable — there is no later point at which the engine would revisit it. This was raised as review note ask #4 on PR #2 and explicitly deferred in `docs/dev_plans/20260710-feature-goal-event-participants.md` (Final Results) as "a genuine, separate behavior gap in the poll loop... warrants its own plan." This is that plan.

**Depends on / reuses:** `docs/dev_plans/20260710-feature-goal-event-participants.md` (Complete) — this plan's backfilled events must land with that plan's `payload.scorer`/`payload.assist`/`payload.team` contract on goal-family types, by reusing the *same* `_event_to_row`/writer path a live match's events already go through. No new payload shape, no side path.

## Requirements

- **Detection**: on a poll where a match is `FINISHED` (or otherwise terminal) with `previous is None`, `was_live is False`, and the bare scoreboard snapshot carries no events (`not match.events`) and no stored `matches` row exists for this provider id — this is "first sight of an already-finished match." Gating on `not match.events` (rather than a provider-type check) is what confines the new behavior to real ESPN-shaped providers without the core engine knowing about provider identity — see Technical Specifications.
  - **`_stored_status_is_live` refactor is a required Phase 1 subtask, not an optional optimization (`/review-plan` finding — the originally-specified "reuse" was infeasible and unsound):** `_stored_status_is_live` (`engine.py:1912-1939`) discards the `rows` it fetches and returns only a `bool`; `was_live == False` is therefore ambiguous between "no stored row at all" and "a stored row exists but is non-live" (e.g. an already-backfilled `FINISHED` match after a restart). Naively treating `was_live == False` as "no stored row" would re-detect and re-fetch an already-backfilled match on every post-restart poll forever, breaking the one-shot/idempotency invariant (Review Focus). **Required fix**: refactor `_stored_status_is_live` (its single call site is `engine.py:1066`) to also surface row-existence — e.g. return the `rows` list itself (empty ⇒ no stored row) instead of a bare `bool`, with the call site deriving both `was_live` (`rows and rows[0][0] in LIVE_STATUS_VALUES`) and the new detection's `no stored row` signal (`not rows`) from that one `_stored_rows_for_provider` call. This keeps the "no second lookup" property (one `_stored_rows_for_provider` call feeds both `was_live` and detection) while being actually implementable — reusing a discarded bool cannot be. This refactor is a named Phase 1 subtask (see Implementation Checklist), not left implicit.
- **One-time fetch, normal path**: on detection, call `fetch_match_detail` once and merge exactly as the existing live/transition branch does (`_merge_detail`), then `hydrated.append(merged)` so the normal `diff_matches` → `_apply` → `_event_to_row` → `PartitionWriter.append_events` chain persists events with the current payload contract. No bespoke write path.
- **Idempotent, one-shot, no double-fetch**: once a match has a stored `matches` row (success or exhausted give-up — see below), it must never be re-fetched for this reason again. A match seen live and *then* finishing is already excluded by construction (`was_live` is `True` for it, so it never satisfies the "first sight" detection above; it stays on the existing live→transition path unchanged).
- **Bounded, non-fatal failure handling**: a `ProviderUnavailableError`/`ShapeDriftError` on this one-time fetch must not crash the poll or the match. Do not immediately persist the bare snapshot on failure (that would create a stored row and permanently foreclose the retry this same "no stored row" detection depends on). Instead retry on subsequent polls up to a small bounded cap, then give up and persist the best-known (scoreboard-only) snapshot. **The cap MUST be a pinned, documented constant (`/review-plan` finding — "a small bounded cap" left unnamed makes give-up tests non-deterministic and is an unnecessary open decision)**: pick a concrete value (e.g. `_BACKFILL_MAX_ATTEMPTS = 3`, mirroring the existing transition-tracker cap's order of magnitude) and document it next to the constant's definition and in `docs/DESIGN.md` (Phase 3). Do not leave the number to be improvised during implementation. **Implementation MUST use a tracker container separate from `self._transitions`** (e.g. a new `self._backfill: dict[str, _TransitionTracker]`) — `self._transitions` membership feeds the `was_live` computation (`engine.py:1058-1060`) and is separately consumed by `_hydrate_vanished_matches` and `_resolve_tracker`/`_emit_give_up`; parking a backfill retry entry in that same dict would flip `was_live` to `True` on the very next poll, misrouting the match onto the live→terminal transition/give-up path instead of retrying as first-sight.
  - **Consume-seam correction (`/review-plan` finding, was under-specified):** `_resolve_tracker`/`_emit_give_up` are called from `_on_durable_snapshot`, which `poll_once` invokes uniformly for every durably-applied snapshot (transitions AND backfill alike) — it has no way to know, from the snapshot alone, which tracker dict a given match belongs to. Parametrizing only the EMIT side (as originally specified) is insufficient: the CONSUME side must also be able to resolve against the correct dict. Required design: the consume-side resolve helper (invoked from `_on_durable_snapshot`) MUST check `self._backfill` in addition to `self._transitions` on every non-live durable apply (e.g. try `self._backfill` first, fall back to `self._transitions`), popping `self._backfill` **on that consume-side resolve** — not at emit time (see the cooldown-bypass bullet below for why emit-time pop is wrong) — so a backfill give-up's `give_up_pending` is correctly resolved and the `self._backfill` entry is popped rather than leaked. This pop happens on **any** non-live durable apply for a tracked backfill match, not only a give-up — a retry that fails once then succeeds also has a live `self._backfill` entry that must be popped on its success apply, or it leaks the same way. See Integration Seams for the explicit writer→reader contract.
  - **Cooldown bypass, not full `_emit_give_up` reuse, and pop-timing MUST be consume-side, not emit-side (`/review-plan` finding — a prior draft of this plan stated both, which are mutually exclusive; consume-side is correct)**: `_emit_give_up` today drives `_abandon` → `_enter_cooldown`, populating `self._cooldowns` — machinery that exists to space out *re-tracking* retries. Backfill give-up is permanent-by-design (post-give-up, "no stored row" detection is `False` forever, so there is never a re-track to space out); reusing `_emit_give_up` verbatim would create an inert-at-best, cross-contaminating-at-worst `self._cooldowns` entry for a match that will never be retried. **Only the give-up SHAPE is shared, not the cooldown side-effect**: backfill give-up persists the merged-never-raw scoreboard snapshot and sets `give_up_pending`, with NO `self._cooldowns` entry created and no call into `_enter_cooldown`. **The `self._backfill` entry is popped by the consume-side resolve helper above, after the give-up write durably lands — NOT by the give-up-emitting code itself.** If the give-up write does not durably land (e.g. the apply is rejected), the entry MUST remain so the give-up re-emits on a subsequent poll, exactly as the transition path's `_emit_give_up` does today (bounded by re-emission, not popped prematurely) — popping at emit time would discard that retry memory and reintroduce an unbounded re-detect/re-fetch loop with none of the transition path's backstops. The shared/reused logic between the transition and backfill paths is "persist scoreboard-only snapshot + mark resolved," not the full `_emit_give_up` chain, and not its pop timing either (transition give-up doesn't pop `self._transitions` at emit — see `engine.py:1582` — backfill give-up must follow the identical discipline for `self._backfill`).
  - **Bypassing `_abandon` must NOT also drop its emission-cap function — this is a separate concern from the cooldown side-effect (`/review-plan` finding — Important: a prior draft only reasoned about `_abandon`'s cooldown effect, missing its emission-cap effect, which is the actual backstop against a give-up write that never durably lands)**: `_abandon` is invoked *inside* `_emit_give_up` (`engine.py:1569-1581`) as an emission cap — `give_up_emissions += 1; if > _MAX_GIVE_UP_EMISSIONS: _abandon(); return` — bounding how many times a give-up can be re-emitted if its apply keeps failing to durably land (e.g. a rejected writer apply, caught before `_on_durable_snapshot`). Bypassing `_abandon` wholesale for its cooldown side-effect (above) removes this bound too unless replaced. **Required**: track a `give_up_emissions` count on the `self._backfill` entry, incremented each time the at-cap short-circuit (below) re-emits; when it exceeds a pinned cap (reuse `_MAX_GIVE_UP_EMISSIONS`, or a dedicated `_BACKFILL_MAX_GIVE_UP_EMISSIONS` if the transition and backfill caps should differ), drop the `self._backfill` entry directly (no cooldown, matching the bypass above) rather than re-emitting indefinitely. This is the backfill-path analog of `_abandon` minus its cooldown effect — not a new invention.
  - **Backfill needs its own pre-fetch at-cap short-circuit, mirroring the transition path's, AND it MUST run before `fetch_match_detail` (`/review-plan` finding — round 2/3/4/5: the ordering was previously unspecified, and an earlier draft misdescribed the consequence of omitting it)**: the transition path short-circuits at `engine.py:1082-1092` — an at-cap tracker with a pending give-up re-emits the give-up and skips the fetch entirely, rather than re-fetching only to fail again. Backfill detection MUST have the equivalent, evaluated **before** `fetch_match_detail` is called. **Correction on consequence (`/review-plan` finding — round 5): omitting this short-circuit does NOT route the match into the raw skip-append branch** — since the at-cap term is deliberately excluded from `is_backfill` (see below), an at-cap match with `previous is None` and no stored row still evaluates `is_backfill == True`, so the skip branch does not fire either way. **The actual consequence of omitting the short-circuit is a wasteful RE-FETCH every poll** (falling through to `fetch_match_detail`, failing again, with no progress) — exactly the cost the transition path's `1082-1092` short-circuit avoids by re-emitting the give-up instead of re-fetching. If `self._backfill.get(match.match_id)` is at-cap with `give_up_pending` set, re-emit the give-up (incrementing `give_up_emissions`, per the bullet above) and `continue` instead of falling through to the fetch.
  - **`is_backfill` signal, computed as a standalone local and used to GATE the existing skip condition — not substituted for it (`/review-plan` finding — Critical: a prior draft of the Phase 1 checklist item set the narrowed skip condition literally equal to this predicate, which inverts the branch)**: `is_backfill` is `previous is None and match.status not in LIVE_STATUSES and not was_live and not match.events and not has_stored_row` — **exactly five terms, matching Requirements' detection bullet; it does NOT include the at-cap term**, since that is handled by the separate pre-fetch short-circuit above (Phase 2), not folded into this predicate (folding it in would make `is_backfill` false for an at-cap match, causing it to fall through to the skip branch instead of the short-circuit). The existing skip condition at `engine.py:1067-1069` (`if match.status not in LIVE_STATUSES and not was_live: hydrated.append(match); continue`) is narrowed by ANDing `not is_backfill`, i.e. `if match.status not in LIVE_STATUSES and not was_live and not is_backfill: hydrated.append(match); continue` — the skip branch fires (append the bare snapshot, as today) exactly when `is_backfill` is `False`; when `is_backfill` is `True`, the branch is skipped and control falls through to the existing try/except at `1093-1095`, per Phase 1's Implementation Checklist. Computing `is_backfill` this way makes it READ in Phase 1 (it gates the branch), not merely assigned for Phase 2's later use — closing the `ruff` F841 risk without inverting the logic. Thread the same value through to Phase 2's except-site branching so a failed first-sight-finished match can be told apart from an ordinary failed live/transition match WITHOUT re-calling `_stored_rows_for_provider`.
- **Cold-start cost is bounded by construction, not by a new rate limiter — verified live (see Findings)**: `fetch_live_matches` returns ESPN's scoreboard for **the current slate only**, per the `fetch_schedule`/`_fetch_scoreboard` docstrings (`src/gamecollect_football/espn.py:809-843` — no `dates` param means "current day"). Live verification against the FIFA World Cup 2026 endpoint (2026-07-12, re-confirmed with a second probe) shows the rollover boundary is **slate-based, not calendar-midnight-based**: the no-`dates` scoreboard response continued to match an explicit `dates=<slate day>` query even after real-world UTC time advanced past midnight into the next calendar date — a match does not roll off until its slate completes, not at a fixed UTC cutoff. The exact slate-flip transition (e.g. what happens once every match in a slate has finished) remains an accepted, named assumption not further probeable without a multi-day observation window. **This same bound is a coverage ceiling, not only a cost bound**: a match that finished on a prior slate has already rolled off the board this plan's detection relies on and can never be backfilled by it — this is the plan's stated scope limit (see Objective), not an assumption carried forward silently. Within that same-slate scope, each first-sight-finished match triggers exactly one `fetch_match_detail` call, structurally identical in cost to an existing live→transition detail fetch, processed sequentially within the same poll exactly as concurrent transitions already are today. No new per-poll cap or queue is introduced by default — see Architecture Decisions for why a naive per-poll cap would break the one-shot/idempotency contract (deferred candidates would get a stored row written anyway via the existing skip-branch fallback, which would then block their retry forever).
- **Opt-out escape hatch, landing in Phase 1 (not deferred)**: add a `backfill_finished_matches: bool = True` keyword to `CollectorEngine.__init__`, defaulting ON, wired to a `--no-finished-backfill` flag on the `collect` CLI subcommand (`src/gamecollect/cli.py`) for an operator who wants to explicitly disable this behavior (e.g. a source known to have a very large historical same-day slate, or a debugging need to reproduce pre-this-plan behavior). Both the constructor flag and the CLI flag ship together in Phase 1, since the feature is ON by default from the moment Phase 1 lands — there must be no window where the behavior is live with no kill switch. No recency-window knob beyond "today's slate" is introduced — out of scope; see Follow-up Work.
- **Two live-network prerequisites, verified against live ESPN 2026-07-12 (see Findings), both gated Phase 1 with an explicit STOP if either had failed** (this is a hard go/no-go, not an assumption to carry forward silently — see Phase 1's first task and Review Focus):
  1. **Scoreboard inclusion — CONFIRMED, with a coverage caveat, and CONFIRMED as a single-match conjunction**: ESPN's default (no-`dates`) scoreboard response for `fifa.world` is scoped to the current slate and is byte-identical in content to an explicit `dates=<today>` query — so a match that finished earlier **the same slate** remains listed and would be seen by `fetch_live_matches`. This was re-verified on **one single match** (`760512`, England v Norway): it finished (`STATUS_FINAL_AET`) and was still present in the default scoreboard response minutes later — proving the conjunction "on-board AND status-terminal" directly, rather than inferring it from two separate matches. A match that finished the **prior** slate (verified: `STATUS_FULL_TIME`, present under `dates=<prior day>`) is **absent** from the default response — it has already rolled off the board. `fetch_schedule` (ESPN-only, not on the `MatchDataProvider` ABC — `ReplayProvider` has no equivalent) is a possible fallback data source for that prior-slate case, but adopting it would mean widening the provider ABC, which is out of scope for this plan (tracked under Follow-up Work). **Scope of this verification (`/review-plan` finding — named explicitly, not left implicit):** all live verification in this plan targeted the `fifa.world` tournament slug only. `espn.py`'s own module docstring (`espn.py:12-14`) already flags that endpoint shape/slug uniformity is unverified beyond `fifa.world`; `DEFAULT_TOURNAMENT` is a constructor parameter, so the collector could in principle run against a different ESPN competition slug with a different slate cadence or scoping behavior. This plan's slate-inclusion and rollover findings are asserted for `fifa.world` and assumed (not verified) to generalize to other ESPN tournament slugs, consistent with the existing codebase caveat.
  2. **Detail-fetch shape — CONFIRMED through the actual collector code path, not just a raw JSON shape check**: `ESPNAdapter().fetch_match_detail('760512')` — the real adapter method this plan wires in, not a raw GET — was invoked directly and returned `status=MatchStatus.FINISHED` with 18 normalized events, 3 of them goal-family, each carrying populated `team`/`player`/`assist` fields (e.g. `{'event_type': 'goal', 'team': 'Norway', 'player': 'Andreas Schjelderup', 'assist': 'Martin Ødegaard', ...}`). Cross-checked against `engine.py`'s `_event_to_row`/`_participant_key`, which remap `player`/`assist` to the `payload.scorer`/`payload.assist` keys for goal-family event types — confirming the plan's `payload.scorer`/`payload.assist`/`payload.team` contract claim end-to-end through the real normalize path, not inferred from a manual JSON read. Both outcomes recorded in `## Findings`.
- **Replay/fixtures are unaffected by construction, not by a special case**: `ReplayProvider.fetch_match_detail` returns the exact same `_snapshot()` as `fetch_live_matches` (`src/gamecollect/replay.py:116-141`) — for a fixture recorded as `FINISHED`, `_snapshot().status` is the fixture's final recorded status *from the very first poll* (`_snapshot`, `replay.py:179-186`, "fixture header state verbatim"), so replay's bare scoreboard snapshot already carries the currently-revealed event prefix directly on `match.events`. The `not match.events` detection gate is therefore naturally `False` for every ReplayProvider poll with any revealed events, and `True` only for a genuinely zero-event first poll (e.g. a step-mode fixture's very first reveal, or a `SCHEDULED`/zero-event fixture) — in that edge case an extra `fetch_match_detail` call is harmless (it does **not** advance the step-mode `_revealed` cursor, `replay.py:124-129` vs `131-141` — only `fetch_live_matches` does) but is still one avoidable call. Confirm in Phase 1 testing whether existing replay/determinism tests assert exact `fetch_match_detail` call counts; if any do, either accept the (harmless, no-op-merge) extra call and update the assertion, or gate the new branch on `provider is not ReplayProvider`-style exclusion as a fallback — decide from what Phase 1 testing actually finds, do not guess ahead of it.

## Review Focus

- **One-shot correctness under partial-poll failure**: verify no code path can create a stored `matches` row for a first-sight-finished match without either (a) a successful detail fetch merged in, or (b) an exhausted retry-cap give-up. Any path that persists the bare snapshot on the *first* failed attempt silently forecloses all future backfill for that match (the "no stored row" detection would never re-fire). Verify this with a **direct** assertion — after the first failed poll, `_stored_rows_for_provider(match_id)` returns empty — not only via the eventual fail-then-succeed end state.
- **No double-fetch for a live→finished match**: confirm the detection condition (`previous is None and not was_live`) is structurally exclusive with the existing `in_transition` (`was_live and not live`) branch — a match must never satisfy both in the same poll. This must be verified with a **structural** assertion (the two conditions cannot both hold, by construction) in addition to the existing behavioral test (a live→finished match doesn't trigger the new branch).
- **Separate tracker container; consume-side dispatch is symmetric with the emit side**: the backfill retry tracker MUST live in a container separate from `self._transitions` (its membership feeds `was_live`, `_hydrate_vanished_matches`, and `_resolve_tracker` — reusing that exact dict for backfill entries would misroute a retrying first-sight match onto the live→terminal transition path on its very next poll). The give-up-persists-merged-never-raw SHAPE is shared between the transition and backfill paths — but NOT the cooldown side-effect (`_abandon`/`_enter_cooldown`), which is bypassed entirely for backfill give-up (see Requirements). Critically, the consume-side resolve helper (invoked from `_on_durable_snapshot` in `poll_once`, uniformly for every durably-applied snapshot) must check `self._backfill` in addition to `self._transitions` — parametrizing only the emit side is not sufficient, since the generic consumer has no way to know which dict a given snapshot's tracker lives in. All three properties are required: separate container, shared give-up shape (not shared cooldown), and symmetric emit/consume dispatch.
- **Restart interaction**: a first-sight-finished match whose backfill retry is exhausted-but-not-yet-given-up when the collector restarts has no durable tracker (trackers are in-memory only, matching today's transition-tracker posture) — confirm the plan's chosen behavior (restart resets its retry budget, i.e. treated as first-sight again) is an accepted, bounded edge case consistent with existing tracker-restart behavior, not a new hidden regression.
- **Give-up is permanent, including across restarts — a consciously accepted risk, not an oversight**: once the retry cap is exhausted and give-up persists the scoreboard-only snapshot, the stored `matches` row makes the "no stored row" detection condition `False` **forever** — the restart-resets-retry-budget note above only helps *before* give-up has written that row; it does nothing after. A transient ESPN outage spanning the entire retry-cap window during this match's one first-sight opportunity therefore permanently forecloses that match's events, with no later poll ever revisiting it (this mirrors the pre-existing gap this whole plan was written to close, now bounded to the retry-cap window instead of to zero attempts). **No escape hatch is introduced by this plan**: give-up persists only the merged-never-raw scoreboard snapshot, with no separate durable "backfill-attempted" marker distinct from the stored row itself — so there is no structural hook for a future periodic/manual re-backfill to target without also re-deriving "which matches gave up vs. succeeded normally," which this plan does not build. This is accepted as consciously scoped, matching the retry cap's own bounded-tolerance intent (a small cap, not indefinite retry) and consistent with the existing `_TransitionTracker` give-up posture elsewhere in the engine; a durable give-up marker enabling manual re-backfill is out of scope here and tracked under Follow-up Work.
- **Live-network prerequisites are a hard gate, not a soft caveat**: Phase 1's first task must have a defined STOP outcome (return to `/dev-plan update`, do not proceed) if either the scoreboard-inclusion or detail-fetch-shape prerequisite (Requirements) fails — a check with no failure branch is not a gate.

### Architecture Decisions
- **Detection reuses the existing stored-row lookup (`_stored_rows_for_provider`) as the one-shot source of truth, rather than introducing new durable state.** Once a first-sight-finished match's events are (successfully) merged and applied, its stored `matches` row exists, which is itself sufficient to make the detection condition `False` on every future poll — no new column, table, or marker is needed for the success path.
- **Failure handling deliberately does NOT persist a stored row on the first attempt**, unlike the existing skip branch's default (`hydrated.append(match)`). This is the key divergence from "just fall back like everything else" — falling back immediately would durably foreclose the retry the detection condition depends on. This is why Phase 2 needs an explicit bounded-retry tracker rather than simply reusing today's per-match isolation `except` clause verbatim.
- **The bounded-retry tracker MUST be a container separate from `self._transitions`; the give-up SHAPE (not the full `_emit_give_up`/cooldown chain) is shared, and the consume side must be symmetric with the emit side.** `self._transitions` membership is read at three other sites — `was_live` (`engine.py:1058-1060`), `_hydrate_vanished_matches` (`engine.py:1225`), and `_resolve_tracker`/`_emit_give_up` (`engine.py:1737` and friends) — all of which treat membership as "this match was live." Storing a backfill retry entry there would make a retrying first-sight match satisfy `was_live` on its next poll, misrouting it onto the live→terminal transition path and corrupting the very retry loop Phase 2 exists to build. The fix is a new `self._backfill` dict, with three properties required simultaneously (satisfying only one or two is a defect):
  1. **State separation**: `self._backfill` membership is never read by `was_live`/`_hydrate_vanished_matches`/any other `self._transitions` consumer.
  2. **Narrower shared logic — only the cooldown side-effect of `_abandon` is bypassed, NOT its emission-cap side-effect (`/review-plan` finding — Important: a prior draft conflated these two effects of `_abandon` and bypassed both, silently dropping the only backstop against a give-up write that never durably lands).** Only the give-up-persists-merged-never-raw *shape* and the emission-cap bound are reused between transition and backfill give-up — NOT the cooldown chain (`_enter_cooldown`). Backfill give-up bypasses `self._cooldowns` entirely (see below), because that machinery exists to space out re-tracking retries, and backfill give-up is permanent-by-design (no re-track ever happens after it) — but it MUST preserve an emission cap (a `give_up_emissions` count on the `self._backfill` entry, bounded by `_MAX_GIVE_UP_EMISSIONS` or a dedicated backfill constant), dropping the entry once exceeded, exactly as `_abandon` does for transitions minus the cooldown write.
  3. **Symmetric consume-side dispatch, with exactly TWO pop paths — not one, and not zero (`/review-plan` finding — round 3 fixed a contradiction where BOTH emit and consume popped; round 5 fixed an overcorrection that then claimed consume was the ONLY pop, contradicting the emission-cap fix in property 2).** `_on_durable_snapshot` (called uniformly from `poll_once` for every durably-applied snapshot) has no way to know, from the snapshot alone, which tracker dict a given match's entry lives in — parametrizing only the EMIT side (as the original design assumed) leaves the CONSUME side unable to resolve a backfill give-up, leaking the `self._backfill` entry and never firing its resolution. The resolve helper invoked from `_on_durable_snapshot` MUST check `self._backfill` in addition to `self._transitions`, and pops the matched entry there — on ANY non-live durable apply for a tracked backfill match (give-up or an ordinary retry-then-succeed), not only when `give_up_pending` is set. **The give-up-EMITTING code MUST NOT pop the entry on a give-up that hasn't yet landed** — that pop is reserved for the consume-side resolve above OR, separately, for the emission-cap exhaustion drop (property 2) once retries are exhausted with no landing. These two pop paths are mutually exclusive by construction (an apply that lands is resolved by the consume side before its emission count could exceed the cap), exactly mirroring the transition path's two pop sites: `_resolve_tracker` on durable apply (`engine.py:1737`) and `_abandon` on emission-cap exhaustion (`engine.py:1596`).
  4. **Backfill needs its own pre-fetch at-cap short-circuit, mirroring the transition path's, evaluated BEFORE `fetch_match_detail` (`/review-plan` finding — round 2/3/4/5: ordering was previously unspecified, and the consequence of omitting it was previously misdescribed).** The transition path short-circuits at `engine.py:1082-1092`: an at-cap tracker with a pending give-up re-emits the give-up and skips the fetch, rather than re-fetching only to fail again. Backfill's equivalent check (`self._backfill.get(match_id)` at-cap with `give_up_pending` set) MUST run before the fetch. **The consequence of getting this wrong is a wasted `fetch_match_detail` call every poll (a re-fetch), NOT a raw `hydrated.append(match)`** — since `is_backfill` deliberately excludes the at-cap term (property 3's Requirements cross-reference), an at-cap match still evaluates `is_backfill == True` and never falls into the skip branch regardless of this short-circuit's placement; the short-circuit exists purely to avoid the wasted re-fetch, not to prevent a raw append.
  5. **`self._backfill` has no vanished-match purge, by accepted design (Minor, named not fixed).** Unlike `self._transitions`, a `self._backfill` entry for a match that rolls off the slate before its give-up lands has no cleanup path and persists until restart — accepted, in-memory only, bounded by matches-per-slate.
- **Backfill give-up bypasses only the cooldown side-effect of `_abandon`, preserving its emission-cap side-effect, and does NOT pop `self._backfill` at emit time — only the consume-side resolve helper does (see above).** `_emit_give_up`'s existing chain (`engine.py:1569-1581`) does two things: (a) populates `self._cooldowns` to space out re-tracking retries for transitions, and (b) increments `give_up_emissions`, calling `_abandon()` once it exceeds `_MAX_GIVE_UP_EMISSIONS` — the bound against a give-up whose apply never durably lands. It also deliberately leaves `self._transitions` un-popped at emit (`engine.py:1582`) so a non-landing give-up re-emits next poll, within that bound. Backfill give-up bypasses ONLY (a) — reusing the cooldown chain verbatim would create an inert-at-best, cross-contaminating-at-worst cooldown entry for a match that will never be retried — but preserves (b): a `give_up_emissions` count on the `self._backfill` entry, checked by the at-cap short-circuit above, dropping the entry (no cooldown) once the cap is exceeded rather than re-emitting forever. The pop-timing discipline (don't pop until the write lands) is not bypassed either; it is exactly what the emission-cap bound and the pre-fetch at-cap short-circuit (property 4 above) depend on.
- **No new per-poll fetch cap / rate limiter — verified live, but the resulting worst-case burst is named explicitly (`/review-plan` finding).** A naive "process at most N first-sight-finished matches per poll, defer the rest" cap was considered and rejected: deferring a candidate within a poll still requires *some* disposition for it that poll (skip it entirely, meaning it falls through to the existing `hydrated.append(match)` skip branch, which persists a stored row and forecloses its own retry — defeating the cap's purpose). Bounding via "ESPN's scoreboard is inherently one day's slate" avoids this correctness trap entirely — confirmed live against `fifa.world` 2026-07-12 (see Findings): the default scoreboard held 1-2 events per slate day across the days sampled. This same slate-day bound is also this plan's coverage ceiling (see Objective/Requirements) — a match from a prior day is never in this response at all, so there is nothing to cap for it; it is simply out of scope. **Named worst-case (unquantified in the sampled days, since a World Cup semifinal/final slate is sparse)**: a cold start mid-dense-slate (e.g. a group-stage slate with 4+ same-day matches) can see all of them first-sight-finished simultaneously, issuing up to that many sequential `fetch_match_detail` calls within a single poll — unlike live transitions, which arrive gradually across polls. The `--no-finished-backfill` kill switch (Requirements) is the accepted mitigation for a source known to have a large same-day slate; this burst scenario is the concrete case it exists for.
- **`not match.events` as the provider-agnostic replay guard**, not a `isinstance(provider, ...)` check — keeps `engine.py` provider-agnostic per existing design (DESIGN.md §7: replay is a first-class provider the engine cannot distinguish from live). See Requirements' Replay/fixtures bullet for the underlying fact (real ESPN board snapshots are always event-empty; replay board snapshots already carry revealed events).
- **If either Phase 1 live-network prerequisite had failed, this plan would not silently degrade.** Both prerequisites are now confirmed (see Findings), so this is a documented contingency rather than a live decision point: a dropped-scoreboard-inclusion finding would have required widening the provider ABC (`fetch_schedule` is ESPN-only today) — out of scope for this plan as written. The plan's response to that outcome would be to STOP and return to `/dev-plan update`, not to improvise an ABC change inline.
- **Give-up is permanent across restarts, by design, with no durable re-backfill escape hatch.** A give-up write persists only the merged-never-raw scoreboard snapshot — the same stored `matches` row the success path writes — with no separate "backfill-attempted" marker distinguishing "gave up after exhausting retries" from "no backfill was ever needed." This means a transient ESPN outage spanning the whole retry-cap window permanently forecloses that match's events, with no restart or later poll able to distinguish and re-target it. This is accepted as consciously scoped (see Review Focus) rather than fixed here; a durable give-up marker enabling a future manual/periodic re-backfill pass is tracked under Follow-up Work, not built in this plan.

## Follow-up Work

- **Prior-day finished-match backfill (out of scope here).** This plan only backfills a match still present on ESPN's default (no-`dates`) scoreboard — i.e. finished the same slate day. A future durable marker (e.g. a `backfill_status` column or a side table) would let an operator identify and manually re-run backfill for matches that gave up during a transient outage, rather than accepting permanent event loss for them. Tracked as future work, not designed here.

## Issues & Solutions

- **Post-merge adversarial Codex review — 4 findings, all one root cause.** A Codex adversarial review of this branch's diff against `main` found that `has_stored_row` was being used as the sole "was backfill already attempted" gate in `_first_sight_finished`, but several paths could durably write a `matches` row without ever completing full detail hydration (permanently blocking retry), while others could retry forever with no cap. Fixed in `src/gamecollect/engine.py`:
  - **Finding #1 [high] — partial scoreboard events silently foreclosed hydration.** `_first_sight_finished`'s `not events` conjunct treated a genuinely first-sight FINISHED match with even one event already on its bare scoreboard snapshot as "nothing to do," persisting the partial list directly and permanently blocking full hydration via `has_stored_row`. Fixed by dropping the `events` conjunct entirely — `ReplayProvider`/the provider ABC already document that a scoreboard-only snapshot may carry a partial event list, so detecting on it regardless is safe (the replay provider's detail fetch is idempotent over the same revealed prefix).
  - **Finding #4 — SCHEDULED/UNKNOWN scope leak.** `_first_sight_finished` used `status not in LIVE_STATUSES`, which also matched SCHEDULED/UNKNOWN (not just FINISHED), detail-fetching every upcoming/unknown fixture on a cold start. Fixed by switching to `_is_terminal(status)` (today: FINISHED only), matching the plan's original "FINISHED (or otherwise terminal)" scope.
  - **Finding #2 [high] — an `_apply` exception downstream of a successful backfill fetch permanently blocked retry.** `seed_match` (seed-before-child-write) could durably write the `matches` row, then `append_events` could raise something `_apply` itself doesn't reconcile (anything but `SequenceError`); `poll_once`'s exception handlers logged and skipped, but `self._backfill` never got a tracker — the stored row then made `has_stored_row` `True` forever with nothing to retry.
  - **Finding #3 [high] — `seed_match` returning `None` after a successful fetch retried unboundedly.** No row was seeded, so `_first_sight_finished` kept re-firing every poll, refetching detail forever with nothing counting against `_BACKFILL_MAX_ATTEMPTS`.
  - **Fix for #2/#3:** a poll-scoped `self._backfill_apply_pending` set (cleared each poll), populated wherever a backfill match's fetch succeeds; `poll_once`'s two exception handlers and its `baseline is None` branch now check membership and, if present, call a shared `_register_backfill_apply_failure` helper (get-or-create the tracker, accrue fallback, `consecutive_failures += 1`) — the existing pre-fetch at-cap check and give-up machinery then take over on the next poll, unchanged. The pre-existing `pending_backfill_retry` OR-clause (kept, not removed) is what keeps `is_backfill` true on the next poll despite `has_stored_row` now reading `True`; its own predicate was tightened from `status not in LIVE_STATUSES` to `_is_terminal(status)` for consistency with finding #4.
  - **A related bug found while tracing the fix (not one of the 4 findings, but would have silently defeated #2/#3):** the pre-existing `backfill_tracker.consecutive_failures = 0` reset on every fetch success (previously harmless dead code, since a successful fetch used to always lead to a durable apply that pops the tracker outright) would otherwise zero the counter immediately before the new downstream-failure registration increments it — masking the cap forever (reset to 0, then +1, every poll). Removed; the reset served no purpose once a durable apply unconditionally pops the tracker via `_resolve_backfill_tracker` regardless of this field's value.

- **Second post-merge adversarial Codex review — 4 more findings, all one shape.** A follow-up Codex review found that `self._backfill` had its own one-shot detection/retry/give-up logic but was never wired into the three mechanisms that already solve the identical class of problem for the sibling `self._transitions` tracker: the restart scan, vanished-match hydration, and cooldown-based permanent-abandonment. Fixed in `src/gamecollect/engine.py` by reusing those existing helpers rather than inventing new parallel state:
  - **Finding #1 [high] — restart loses an in-flight backfill retry.** A daemon restart across a `seed_match`-durably-written but not-yet-fully-hydrated first-sight-finished match lost its `self._backfill` tracker (process-local only); the row then made `has_stored_row` `True` forever with no tracker to keep retrying. IS NULL`), resolves the provider id via the existing `_resolve_stored_provider_id`, and seeds a fresh (zero-failure) `self._backfill` tracker. Accepted false positive, documented in the method's docstring (same tone as the pre-existing "Residual gap" note): a genuinely scoreless FINISHED match is indistinguishable from a partially-failed backfill by this heuristic — restart harmlessly re-attempts one redundant, idempotent `fetch_match_detail` for it if it ever reappears.
  - **Finding #2 [high] — an unpersistable backfill give-up hot-looped forever.** `_emit_backfill_give_up`'s emission-cap exhaustion branch popped the tracker with no durable marker; if the give-up snapshot's OWN apply never landed (e.g. a permanently unseedable identity), `has_stored_row` never became `True`, so `_first_sight_finished` re-fired from scratch on the very next poll — an unbounded fetch/give-up cycle. Fixed by calling `self._enter_cooldown(...)` (the same helper `_abandon` uses) in that exhaustion branch, and gating the `is_backfill` computation's `_first_sight_finished` call on a caller-side `and not self._cooling_down(...)` (the pure predicate itself stays untouched, per its own "evaluated separately" documented exclusion pattern). `pending_backfill_retry` needs no equivalent gate — it already can't fire once the tracker is popped. This is a deliberate, documented downgrade of the old "backfill give-up is permanent-by-design" framing: that framing only holds when the give-up write actually lands durably.
  - **Finding #3 [medium] — vanished-match hydration ignored mid-retry backfill trackers.** `_hydrate_vanished_matches`'s tracked set only considered `self._last`/`self._transitions`; a match with an active `self._backfill` tracker that dropped off the slate before its next poll leaked its tracker forever, never retried or given up on. Fixed with a second pass, `_hydrate_vanished_backfill_matches`, using ONLY the backfill give-up/cap helpers (`_backfill_tracker`, `_backfill_tracker_at_cap`, `_emit_backfill_give_up` — never the transitions equivalents, preserving the `is_backfill`/`in_transition` mutual-exclusivity invariant). Base resolution does not reuse `_transition_base` (transitions-specific, reads `self._last`/the stored row): a vanished backfill candidate has neither by `_first_sight_finished`'s own conjuncts, so the only admissible base is the tracker's accrued `fallback`.
  - **Finding #4 [medium] — unbounded per-poll backfill fetch volume.** The main loop detail-fetched every `is_backfill`-eligible match sequentially with no cap, so a cold start against a slate with many already-finished matches (or a provider outage) could serialize a large/slow burst inside one poll. Fixed with a new `_BACKFILL_MAX_FETCHES_PER_POLL = 5` constant and a poll-scoped (local, not instance-attribute) counter in `_fetch_poll_snapshots`: once the budget is exhausted, a pending-retry candidate is deferred without touching its failure count, and a fresh first-sight candidate gets a zero-failure tracker seeded (marking it pending) WITHOUT persisting its bare scoreboard snapshot — appending it would durably write the row and reintroduce the finding-#1-class permanent-block bug. Deliberately NOT applied to the vanished-match backfill pass (Fix #3), which is structurally bounded by how few matches can be mid-retry before vanishing.
  - New regression tests in `tests/test_engine.py`: `test_restart_seeds_backfill_tracker_for_terminal_zero_event_row_and_hydrates` + `test_restart_backfill_scan_skips_row_whose_id_is_on_slate_or_already_tracked` (#1), `test_backfill_give_up_exhaustion_enters_cooldown_then_resumes_detection` (#2), `test_vanished_backfill_match_is_retried_and_given_up_via_vanished_hydration` + `test_vanished_backfill_match_never_touches_transitions_tracker` (#3), `test_backfill_per_poll_fetch_budget_bounds_burst_and_defers_rest` (#4). One pre-existing test's premise was invalidated by finding #2's fix and was renamed and reworked: `test_backfill_unpersistable_give_up_bounded_reemits_then_drops_then_refetches_once` → `test_backfill_unpersistable_give_up_bounded_reemits_then_cools_then_refetches_once` (an unpersistable give-up now cools down instead of re-detecting on the very next poll; the test drives `_COOLDOWN_BASE_POLLS` additional polls to prove both the suppression and the eventual resumption).
- **Third post-merge adversarial Codex review — 5 more findings.** A third Codex review found that the second round's own fixes (restart-scan seeding, the per-poll fetch budget) each closed one gap while opening or leaving open a narrower one — the pattern the global commit-hygiene note about "one fix breaking a different code path that relied on the same mechanism" describes. Fixed in `src/gamecollect/engine.py`:
  - **Finding #1 [high] — a transient non-terminal status reset silently discarded an active backfill retry, via a different path than round 2 closed.** `pending_backfill_retry`'s `_is_terminal(match.status)` conjunct (added in round 2 for consistency with `_first_sight_finished`) meant a tracked match whose board momentarily regressed to SCHEDULED/UNKNOWN (the provider ABC does not guarantee status monotonicity) flipped `is_backfill` to `False` for that poll, routing it into the generic direct-persist skip branch: the raw non-terminal snapshot got baselined into `self._last`, and `_resolve_backfill_tracker` (pops on ANY durable apply) silently dropped the tracker — permanently foreclosing re-detection even if the match later turned FINISHED again. Fixed by widening `pending_backfill_retry`'s status conjunct back to `match.status not in LIVE_STATUSES` (its job — "keep an ALREADY-tracked match routing through backfill regardless of momentary status" — is narrower than, and must diverge from, `_first_sight_finished`'s own unchanged terminal-only new-candidate gate). This alone reopened a second gap: a fetch that then succeeds but is ALSO still inconclusive (both scoreboard and detail SCHEDULED/UNKNOWN) fell through to the unconditional `hydrated.append(merged)`, persisting a non-terminal snapshot and popping the tracker the same way. Closed with a new `elif is_backfill and merged.status not in LIVE_STATUSES and not _is_terminal(merged.status)` branch (structurally mutually exclusive with the adjacent `in_transition` branch by construction) that instead calls the existing `_register_backfill_apply_failure` helper and, at cap, `_emit_backfill_give_up` — treating the inconclusive fetch as a bounded attempt rather than a durable write.
  - **Finding #2 [high] — the restart scan's on-slate guard, narrowed from the transitions scan's, wrongly skipped an incomplete row still on the current slate.** `_seed_restart_backfill_trackers` reused `_seed_restart_trackers`'s "skip if any mapped id is on the slate at all" guard verbatim; that guard's rationale (a live slate match is naturally re-detected via `was_live`) does not hold for the backfill scan, since `has_stored_row` reads `True` regardless of slate presence. An incomplete terminal row whose match reappeared on the current slate (even still reporting the identical non-live status) fell into the same generic direct-persist skip branch as finding #1, permanently losing its events. Fixed by narrowing the guard to "skip only if a mapped id is on the slate reporting a LIVE status right now" — `_fetch_poll_snapshots` now computes `live_slate_ids` (a strict subset of `slate_ids`) and passes that, not the full slate, into the scan. The genuine multi-provider safety concern (a live sibling id must not be wedged) is preserved; the false-guard case (a non-live reappearance) is not.
  - **Finding #3 [high] — the vanished-match backfill pass had no fetch budget, defeating the per-poll cap finding #2's fix reintroduced a path around.** `_hydrate_vanished_backfill_matches` was deliberately left unbounded (reasoning: "structurally much smaller" than a cold-start slate) — but finding #2's widened restart seeding can now seed many backfill trackers for historical incomplete rows in one restart poll, most immediately off-slate and eligible for this pass in the same poll, reintroducing the unbounded burst the per-poll cap exists to prevent. Fixed by threading the shared `_BACKFILL_MAX_FETCHES_PER_POLL` budget (as a `remaining_backfill_budget` parameter, computed at the call site as the budget minus what the on-slate loop already consumed) through `_hydrate_vanished_matches` into `_hydrate_vanished_backfill_matches`; once the local fetch count in that pass's own loop reaches the remaining budget, every subsequent candidate is deferred (no fetch, no failure recorded) rather than fetched.
  - **Finding #4 [medium] — the restart heuristic can re-attempt an already-exhausted give-up; ACCEPTED, MITIGATED, NOT FULLY CLOSED.** `_seed_restart_backfill_trackers`'s terminal-plus-zero-events heuristic cannot distinguish a genuinely-interrupted backfill from a match that already went through `_emit_backfill_give_up`'s bounded exhaustion path and had a scoreboard-only terminal snapshot durably persisted as its accepted final state — a later restart re-seeds a tracker for it and repeats one doomed fetch/fail/give-up cycle. Properly closing this needs a durable marker distinguishing "interrupted" from "already gave up" (a new column or `matches.payload` key) — deliberately OUT OF SCOPE for this task (a schema/payload-shape decision that should not be improvised under a fix-loop). What finding #3's fix DOES do: bound the residual cost from "unbounded repeated outage-scale load" to "a bounded, occasional, wasted retry cycle after a restart, gated by the same per-poll budget as everything else" — documented explicitly in `_seed_restart_backfill_trackers`'s docstring as an accepted, known gap, in the same tone as the file's pre-existing "Residual gap"/"Accepted false positive" notes. A pre-existing test (`test_backfill_given_up_match_not_refetched_after_restart`) asserted the OLD, now-intentionally-changed invariant ("never re-fetched after restart"); renamed to `test_backfill_given_up_match_re_seeded_bounded_after_restart` and reworked to assert the new bounded, idempotent behavior (exactly one re-fetch, no durable change when nothing new is reported).

Note: the third claimed staleness this finding named — detection requiring an empty scoreboard event list — was NOT found in the doc's current text; that claim was apparently already corrected by round 1's finding #1 fix (which dropped the `events` conjunct from `_first_sight_finished`) before this round began, so no further doc change was needed for that specific claim.

## Final Results

Phase 1 landed detection (`is_backfill`, gated on `previous is None`, non-live status,
no in-memory or stored baseline, and an empty scoreboard event list) and the one-time
`fetch_match_detail` call, reusing the existing `_merge_detail`/`diff_matches`/`_apply`
write path so a first-sight-finished match's events land through the same
`_event_to_row` contract as a live match's — no bespoke write path, and gated behind a
`backfill_finished_matches` constructor flag / `--no-finished-backfill` CLI switch, on
by default. Phase 2 added bounded, non-fatal retry: failed fetches are tracked in a
`self._backfill` container kept separate from `self._transitions` (so a retrying match
never misroutes onto the live→terminal transition path), capped at
`_BACKFILL_MAX_ATTEMPTS`, and a give-up path that persists the best-known
scoreboard-only snapshot (shape shared with the transition give-up path, cooldown
side-effect bypassed for an ordinarily-landing give-up since it is durably permanent)
with a symmetric consume-side resolve so `self._backfill` entries are never leaked.
Phase 3 verified the detection/backfill/give-up flow end-to-end against
`ReplayProvider` fixtures and documented the feature (including its accepted
same-slate scope limit) in `docs/DESIGN.md`. A second post-merge review round (see
Issues & Solutions) closed the remaining gaps where `self._backfill` had its own
parallel state instead of reusing the transitions tracker's restart scan,
vanished-match hydration, and cooldown-abandonment mechanisms — including bounding
the one case where an unpersistable give-up snapshot is NOT permanent (its cooldown
now bounds the retry cycle) and adding a per-poll fetch-volume cap. A third
post-merge review round found that each of round 2's fixes had a narrower edge case
of its own: a transient non-terminal status regression on an already-tracked match
could still silently discard its retry via a different code path (fixed by widening
`pending_backfill_retry` and adding a new inconclusive-fetch-success branch); the
restart scan's on-slate guard, copied from its transitions sibling, wrongly skipped
seeding for an incomplete row that reappeared non-live on the slate (fixed by
narrowing the guard to only skip a LIVE sibling id); and the widened restart seeding
reintroduced the unbounded-burst problem through the previously-unbounded
vanished-match backfill pass (fixed by threading the shared per-poll budget into it).
One finding — the restart heuristic's inability to distinguish an interrupted
backfill from an already-given-up match — was deliberately mitigated (bounded by the
per-poll budget) and documented as an accepted, known gap rather than fully closed;
closing it needs a durable give-up marker, a schema/payload decision intentionally
left out of this task's scope. `docs/DESIGN.md` was updated to match: the shared
per-poll budget and its deferral semantics, and give-up permanence being conditional
on the give-up snapshot's own apply landing durably.
